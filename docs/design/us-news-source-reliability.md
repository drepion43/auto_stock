# 미국 뉴스 소스(GDELT) 신뢰성 문제 — 현황과 선택지

> 작성일: 2026-10-12
> 상태: **문제 정리 — 사용자 결정 대기** (§5 결정 필요)
> 관련: `news-sentiment.md`(GDELT 도입 배경, "rate limit 실측 미완료" 항목의 답), `main-agent-migration-plan.md`(eval에서 발견), 커밋 `04ad247`

## 1. 요약

- 나스닥 종목 분석에서 **"최근 뉴스 감성 확인하지 못함"이 반복**된다. 메인 루프 전환 eval(2026-10-11~12)에서 엔비디아 분석 6회 모두 뉴스 조회가 실패했고, 구 루프·새 루프 모두 같았다(루프 전환과 무관).
- 직접 원인은 **GDELT DOC 2.0 API의 요청 제한(HTTP 429)**이다. 요청 간격 조절·재시도·검색어 개선을 적용해 개선은 됐지만(커밋 `04ad247`), **GDELT의 제한이 공지보다 훨씬 엄격하고 응답도 느려** 근본 해결은 아니다.
- 결정할 것: 미국 뉴스를 계속 GDELT로만 받을지, 캐시를 붙일지, 다른 무료 소스를 추가할지(§4).

## 2. 확인된 사실 (2026-10-12 라이브 실측)

| # | 사실 | 근거 | 신뢰도 |
|---|---|---|---|
| F1 | GDELT는 과다 요청 시 HTTP 429와 함께 `"Please limit requests to one every 5 seconds..."`를 반환한다 | `requests.get` 직접 호출 응답 본문 | HIGH |
| F2 | **5초 간격으로는 부족하다.** 짧게 몰아 보낸 직후에는 6초·12초·30초 간격에도 429가 섞였다 | 간격을 바꿔 가며 3차례 호출 | HIGH(현상), 원인(IP 단위 누적 제한 추정)은 MEDIUM |
| F3 | 요청 간격 조절(5.5초) + 429 시 15초 지연 후 1회 재시도를 적용해도, 연속 2건 중 1건이 다시 429로 실패했다 | `"NVIDIA"` 성공(50건), `"APPLE"` 재시도 후에도 429 | HIGH |
| F4 | 응답이 느리다 — 성공한 검색 1건에 대기 포함 **43초** | 위 호출의 경과 시간 | HIGH(1회 측정) |
| F5 | SEC 법인명으로 정확구문 검색하면 기사를 대부분 놓친다 — 최근 14일 `"NVIDIA CORP"` **27건** vs `"NVIDIA"` **50건 이상**(상한에 걸림) | 간격을 둔 개별 호출 | HIGH |
| F6 | 같은 eval에서 기술 지표 "산출 오류"도 났지만 이건 **별개 원인**(서브에이전트 도구 병렬 실행 + DuckDB 연결 공유)이며 `04ad247`에서 해결됐다 | 병렬 호출 재현 → 수정 후 NVDA 분석에서 SMA/RSI/MACD 정상 | HIGH |

### 왜 우리 쪽 호출이 몰리는가

- `stock_analyst` 서브에이전트는 공시·뉴스 등 여러 도구를 한 응답에 묶어 부른다(LangGraph가 병렬 실행).
- 관련기업 분석은 종목 최대 5개를 연달아 딥다이브하고, `find_related_companies`의 공동언급 검증도 GDELT를 쓴다.
- 백그라운드 추천 배치는 후보 수십 종목을 처리하며 종목마다 뉴스를 조회할 수 있다.
- 즉 질의 1건이 GDELT 요청 수 건~수십 건으로 번진다. GDELT의 공개 무료 API는 이런 사용량을 전제로 하지 않는다(429 본문이 대량 사용자는 별도 데이터셋으로 옮기라고 안내).

## 3. 이미 적용한 수정 (커밋 `04ad247`)

| 수정 | 내용 | 효과 |
|---|---|---|
| 요청 간격 조절 | `gdelt_source`가 프로세스 전체 요청을 5.5초 간격으로 직렬화(스레드 공유 잠금) | 우리가 스스로 만드는 429를 줄임 |
| 429 재시도 | 429를 받으면 다음 허용 시각을 15초 뒤로 미루고 1회 재시도 | 일시적 제한은 넘김. F3처럼 지속 제한은 못 넘김 |
| 검색어 개선 | `company_phrase()`: 따옴표 제거 + SEC 법인 접미사(Corp, Inc, Co, Ltd, PLC, Holdings, Group, /DE/ 등) 제거. GDELT 호출부 4곳(채팅 도구, 배치 파이프라인, 관련기업 공동언급 검증, 검증 스크립트) 공통 적용 | 검색되는 기사 수 증가(F5) |

**수정이 만든 새 비용**: 요청이 직렬화되고 대기가 생겨 **뉴스가 필요한 미국 종목 질의의 응답이 느려질 수 있다**(연속 요청 시 건당 최소 5.5초, 429 시 +15초). 대화형 챗봇 체감 지연에 직접 영향.

**알려진 부작용(검색어 개선)**: 흔한 단어와 겹치는 회사명(Apple, Meta, Oracle 등)은 무관한 기사가 섞일 수 있다. 감성 해석 LLM이 관련성을 일부 거르지만 완벽하지 않다. 문제가 관찰되면 예외 목록(원래 이름 유지)을 둔다.

## 4. 선택지

| 선택지 | 내용 | 장점 | 단점·위험 |
|---|---|---|---|
| **A. GDELT 유지 + 결과 캐시** | 검색어별 결과를 일정 시간(예: 1시간) 저장해 같은 종목 반복 조회 시 재요청하지 않음(DuckDB 또는 메모리) | 무료, 변경 범위 작음, 배치·관련기업 분석처럼 같은 종목을 여러 번 보는 경로에서 효과 큼 | 처음 보는 종목은 여전히 실패·지연. 뉴스가 최대 1시간 늦을 수 있음 |
| **B. 다른 무료 소스 추가(폴백 또는 대체)** | 후보: yfinance 종목 뉴스, Google News RSS 등. GDELT 실패 시 폴백으로 쓰거나 주 소스로 교체 | 실패율·지연 대폭 감소 가능 | **미검증** — 비공식 경로가 많아 언제든 막히거나 형식이 바뀔 수 있음. 이용약관 확인 필요. 새 소스 모듈·테스트 작업 |
| **C. 유료 뉴스 API** | NewsAPI, Polygon, Finnhub 등 | 안정성·속도·문서화 | 비용 발생. 프로젝트의 "무료 소스 전용" 원칙(`etf-composition-analysis.md`의 미국 ETF 결정 등)과 충돌 |
| **D. 현행 유지** | 지금 수정만으로 운영 | 추가 작업 없음 | 뉴스 신호가 자주 비어 미국 종목 추천 품질 저하 지속 |

**추천: A를 먼저 적용하고, 병행해서 B를 조사한다.**
- A는 위험이 낮고 바로 효과가 있다(특히 관련기업 분석·배치처럼 같은 종목을 여러 번 보는 경로).
- B는 후보 소스마다 공식성·이용약관·라이브 안정성을 먼저 확인한 뒤 채택 여부를 다시 결정한다(이 프로젝트의 "라이브 검증 후 채택" 관례와 동일).

## 6. 검증 방법 (선택지 적용 후)

- 같은 미국 종목 5개(예: NVDA, AAPL, MSFT, TSLA, AMZN)에 대해 `tool_analyze_news_sentiment`를 연속 호출 → 성공률, 종목당 지연, 429 발생 수를 수정 전후로 비교.
- eval Q7("엔비디아 사도 돼?") 3회에서 "뉴스 감성 확인하지 못함" 문구가 사라지는지 확인.
- 미국 종목 관련기업 분석 질의(예: "엔비디아 관련기업 분석해줘")에서 공동언급 검증 성공률 확인.
