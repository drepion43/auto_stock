# 검토 보고서 — 대화형 에이전트 챗봇 아키텍처 (deepagents 도입 범위)

> **후속 결정 (2026-10-11~12)**: 이 보고서가 내린 "메인 대화 에이전트는 네이티브 tool-calling 루프 유지" 결론은 사용자의 범용성 확장 결정으로 **번복**됐다 — 메인 루프는 이제 `create_deep_agent` 기반(`chat_agent/deep_loop.py`)이 기본이다. 번복 근거·계획·eval 결과는 `main-agent-migration-plan.md`. 아래 본문은 당시 판단 기록으로 그대로 둔다.

> 보고일: 2026-08-29
> 보고 대상 문서: `docs/design/chat-agent-plan.md`, `docs/design/news-disclosure-plan.md`
> 검토 방식: 4개 역할(사실·정합성 / 시니어 엔지니어 / 보안·리스크 / 일관성 검토자) 병렬 검토 후 종합

## 1. 배경 및 목적

`docs/design/chat-agent-plan.md`가 정의한 궁극 목표(주식 전문 대화형 에이전트 챗봇)를 향해 가는 중, 세 가지 안건이 제기되어 착수 전 검토 회의를 진행했다.

1. 이 로드맵 자체가 실행 착수 가능한 수준으로 계획됐는지
2. 뉴스/공시 분석(#4)을 plain function tool로 두기로 한 기존 결정이 타당한지
3. 사용자 질의("삼성전자 추천 금액대?")에 답하기 위해 업종 분류를 넘어선 **"유기적으로 연결된 기업"**(공급망·고객사 등)까지 함께 분석하려면 deepagents 도입이 필요한지

## 2. 안건별 논의 및 결론

### 안건 1. `chat-agent-plan.md`는 실행 착수 가능한 수준인가

**결론: 방향은 맞으나, 실행 설계로는 미완성 — B단계 착수 전 3가지 공백을 메워야 한다.**

사실·정합성 검토 결과, 문서 스스로 "B단계 착수 시 재구체화한다"고 인정하고 있어 과장된 주장은 없었다. 다만 실제로 비어 있는 부분이 확인됐다:

| 공백 | 내용 |
|---|---|
| 종목명→티커 해석 | "삼성전자" 같은 자연어 질의를 티커(`005930`)로 바꾸는 단계가 문서 어디에도 설계돼 있지 않음 |
| 메인 대화 에이전트의 런타임 | LLM차트분석(#3)의 프로바이더(OpenAI)는 정해졌으나, 사용자 질의를 받아 tool을 고르는 **메인 에이전트 자체**의 모델/SDK는 미확정 |
| "신호 없음" 응답 설계 | 규칙엔진 후보가 없는 경우(실제로 라이브 테스트에서 흔히 발생) 챗봇이 어떻게 답할지 미설계 |

### 안건 2. 뉴스/공시(#4)를 plain tool로 두는 결정

**결론: 타당함 — 유지.**

`resolve_corp_code`(캐시 조회 후 미스 시 재다운로드)와 `fetch_disclosures`(고정 파라미터 조회) 모두 "몇 단계를 더 쓸지" 판단하는 로직이 없는 결정론적 함수 체인 + LLM 단일 구조화 호출이라는 계획서의 주장이 실제 설계와 일치한다. 일관성 검토에서도 이 결정이 "관련기업 탐색을 agent로 분류"한 판단과 **같은 기준(자율 다단계 판단 필요 여부)의 일관된 적용**이라는 점이 확인됐다 — 자의적 구분이 아니다.

**경미한 보완 필요**: `corpCode.xml`이 zip 압축 파일이라는 사실이 배경 절에 언급만 되고, Phase 0 검증 체크리스트에 "압축 해제 방식 확인" 항목이 명시적으로 없다. 사소하지만 Phase 0에서 놓치기 쉬운 지점이라 체크리스트에 추가 필요.

### 안건 3. "관련기업 탐색" — deepagents가 필요한가

**결론: 기능 필요성은 인정하나, 구현 수단은 deepagents가 아니라 "예산 상한을 둔 수동 tool-use 반복 루프"로 수정한다.**

이 안건이 이번 회의에서 가장 중요한 결론 변경이다.

- **필요성 자체는 유효하다**: 업종 분류만으로는 실제 공급망·고객사 관계를 놓친다는 문제 제기는 타당하고, 이 관계를 찾는 작업이 "정해진 소스만 보는 게 아니라 열린 판단"이 필요하다는 점도 맞다.
- **그러나 시니어 엔지니어 검토에서 deepagents(LangGraph) 채택은 기각됐다.** 이유:
  1. 실제 작업은 "후보 생성 → DART/뉴스로 검증 → 필요시 1~2회 추가 탐색"이라는 **최대 2~3회면 끝나는 유한 반복**이다. LangGraph가 실제 가치를 갖는 조건(여러 턴에 걸친 상태 유지, 복잡한 분기 사이클, 체크포인트/재개)에 해당하지 않는다.
  2. 이 프로젝트는 이미 ML(#2)·LLM차트(#3)·메인챗봇 설계까지 **세 차례 연속** "프레임워크는 실제 필요가 검증된 뒤" 원칙으로 deepagents를 기각해 왔다. 여기서만 도입하면 프로젝트 전체에서 유일하게 상태그래프 패러다임이 하나 더 생기고, 결정론적 모킹 테스트·80% 커버리지 원칙과 충돌하는 비결정적 루프를 테스트해야 하는 부담이 추가된다.
  3. **동일한 이득을 `max_iterations` 상한을 둔 수동 while 루프**로 얻을 수 있다 — 기존 `OpenAIChartClient`류 Protocol 패턴과 모킹 테스트 방식을 그대로 재사용 가능.
- **보안·리스크 검토가 이 결론에 안전장치를 추가했다** (구현 방식과 무관하게 반드시 필요):
  1. **환각 방어**: LLM이 주장한 기업 관계를 그대로 쓰면 안 됨 — DART 공시(주요 매출처·특수관계자)나 뉴스로 **사후 검증**하는 tool 호출이 설계에 포함돼야 한다. 관계 판단이 틀리면 그 위에 얹히는 4개 신호 분석 전체가 엉뚱한 종목에 적용되는 더 큰 파급 위험이 있다.
  2. **비용 상한 필수**: `llm_chart_analyst/client.py`의 `max_calls_per_run` 같은 호출 예산 + **탐색 깊이 제한**이 반드시 있어야 한다 — 없으면 질의 1건이 재귀적 연쇄 탐색으로 이어져 수십~수백 회 API 호출로 번질 수 있다.
  3. 크리덴셜 노출의 신규 위험은 적으나, 향후 이 기능이 웹 원문 크롤링으로 확장되면 원문 텍스트가 프롬프트·로그에 그대로 노출되는 새로운 위험이 생기므로 그 시점에 별도 검토 필요.

## 3. 문서 갱신 필요 사항 (일관성 검토 지적)

이번 회의의 결론(관련기업 탐색을 별도 agent 후보로 분류)이 **현재 어떤 문서에도 기록돼 있지 않다.** `chat-agent-plan.md`의 E단계 서술은 지금 "#4를 sub-agent로 승격할지 재판단"만 언급할 뿐, "관련기업 탐색"이라는 완전히 별개의 신규 capability는 언급이 없다 — 이대로 두면 향후 이 문서를 보는 사람이 두 개념을 혼동할 위험이 있다.

**필요한 갱신**:
- `chat-agent-plan.md` "핵심 설계 결정 2"의 tool 후보 예시(`position_sizing`, `get_price_data`)에 "관련기업 탐색"을 추가하되, 앞의 둘은 **plain tool 후보**, 이것은 **agent(수동 반복 루프) 후보**라는 차이를 명시
- E단계 로드맵 서술에 "#4 sub-agent 승격 재판단"과 "관련기업 탐색 신규 착수 재판단"을 별개 항목으로 분리 기재
- `news-disclosure-plan.md` Phase 0 검증 체크리스트에 "`corpCode.xml` 압축 해제 방식 확인" 추가

## 6. 2차 회의 (같은 날) — "관련기업 전체 재분석 + 통합 판단" 제안 검토

### 배경

사용자 추가 제안: 관련기업(예: 하이닉스·제주반도체·삼성전기·애플 — 업종뿐 아니라 경쟁사·납품사·부품제공업체 포함) 각각에 대해 **별도 sub-agent**를 만들어 ML예측+LLM차트분석+뉴스공시 3개 분석을 수행·통합하고, 대상 종목(삼성전자) 자체도 동일 3개 분석을 수행해 관련기업들의 변동성이 대상 종목에 미치는 영향과 최종 판단·근거를 사용자에게 제공하자는 것. 시니어 엔지니어/보안·비용 리스크/일관성 검토자 3개 역할로 재검토했다.

### 결론 요약

| 안건 | 결론 |
|---|---|
| ④ 종목별 sub-agent 필요 여부 | 불필요 — plain tool(ML/LLM차트/뉴스공시) 반복 호출 + `asyncio.gather` 병렬화로 충분 |
| ⑤ 호출 예산 상한 | 기존 `max_calls_per_run`(배치 스캔 전제)은 대화형 질의 단위에 부적합 — 질의 단위 상한 신설 필요 |
| ⑥ 문서 반영 | `chat-agent-plan.md`에 "관련기업 각각에 기존 tool 반복 적용 + 교차 영향 종합" 문장 추가 필요 |

### 상세 논의

**④ sub-agent 불필요, plain tool 반복 호출로 충분**

시니어 엔지니어 검토: "종목 X에 ML예측·LLM차트분석·뉴스공시분석을 수행하라"는 자율 판단이 필요 없는 고정 3단계 절차이며, 세 함수 모두 "정해진 입력→구조화된 출력" 단일 계산이다. 관련기업이 여러 개라고 해서 이 분석 자체의 성격이 바뀌지 않는다 — 이미 존재하는 오케스트레이터의 `_ml_reasons`/`_llm_reasons`/`_news_reasons` 헬퍼를 종목 리스트에 반복 적용하는 것과 동형이다. 종목당 별도 sub-agent를 두면 얻는 이득은 없고(각 종목 분석이 서로 독립적이라 자율성이 발휘될 지점이 없음), 오케스트레이션 복잡도·실패격리 계약의 5배 복제·테스트 부담만 커진다.

일관성 검토도 같은 결론에 도달했다: `chat-agent-plan.md` 배경 절이 애초에 "메인 에이전트가 관련 분석을 필요한 것만 골라 병렬로 호출"한다고 정의했고, 핵심 설계 결정 1이 "3개 tool 동시 요청" 같은 다중 tool 호출을 이미 네이티브 tool-calling으로 처리하도록 설계해 뒀다 — 관련기업이 4개면 "3개 tool × 4종목 = 최대 12회 호출"일 뿐, 문서가 이미 약속한 능력의 연장선이다. 다만 "sub-agent"라는 명명 자체가 부정확한 프레이밍이라 이대로 기록하면 향후 "분석이 agent가 됐다"는 오독을 유발할 수 있다는 지적이 있었다.

**지연시간**: 15회(5종목×3분석) 순차 실행은 느리지만, `asyncio.gather`(로드맵이 이미 전제한 방식)로 종목 단위 병렬화하면 "가장 느린 종목 1개" 수준으로 수렴 — 별도 아키텍처 없이 기존 코드 구조로 해결 가능.

**⑤ 호출 예산 상한 — 질의 단위로 신설 필요**

보안·비용 리스크 검토: 기존 `max_calls_per_run`(기본 20, `llm_chart_analyst/credentials.py`)은 "배치 스캔 프로세스 1회 실행"을 전제로 설계된 상한이라, 상시 구동되는 대화형 챗봇에 그대로 쓰면 "20"이 하루 전체 대화의 총 호출 상한이 돼버려 사용자가 질의 몇 번만 해도 소진된다. **질의(턴) 단위로 리셋되는 별도 상한**이 필요하다: `MAX_TICKERS_PER_QUERY`(관련기업 확장 개수 상한, 권장 3~5개), `MAX_LLM_CALLS_PER_QUERY`(질의당 LLM 총 호출 상한, 권장 6~8회). 상한에 걸리면 "일부만 분석했다"고 사용자에게 명시해야 한다.

**환각 복합화**: 관련기업 판단이 틀리면 그 위에 얹는 LLM차트분석·뉴스공시 해석은 애초에 틀린 종목에 대한 것이라 무의미해진다. 5종목×2개 LLM 신호가 섞이면 "확인된 관계 기반 분석"과 "추정 관계 기반 분석"이 최종 답변에서 뭉뚱그려질 위험이 크다 — **관계별 "확인됨/추정됨" 플래그를 최종 답변까지 전파**하고, 확인 안 된 관계 기반 분석은 confidence를 한 단계 낮추거나 별도 문단으로 분리 표기해야 한다.

**⑥ 문서 반영 필요**

일관성 검토: 원래 로드맵 E단계는 "관계 탐색" 자체만 다뤘고, "찾은 기업들 전체에 3개 분석을 재수행해 변동성 파급을 종합 판단"하는 부분은 없다 — 새 아키텍처는 아니지만(배경 절이 이미 약속한 능력의 실사용 예시), 로드맵 E단계 또는 핵심 설계 결정 3 아래에 "관련기업 발견 후 각각에 기존 3개 tool을 반복 적용 + 메인 에이전트가 교차 영향을 종합"이라는 문장을 명시적으로 추가해야 한다.

### 종합 결론 (2차)

사용자의 제안 방향("관련기업까지 함께 분석해 대상 종목 판단에 반영") 자체는 타당하고, 이미 `chat-agent-plan.md`가 예정해 둔 능력의 자연스러운 확장이다. 다만:

- **"sub-agent"라는 구현 수단은 불필요** — 기존 plain tool(ML/LLM차트/뉴스공시) + `asyncio.gather` 병렬 반복 호출로 충분
- **새로 반드시 필요한 것은 질의 단위 호출 예산 상한**(종목 수·LLM 호출 총량)과 **관계 확인 여부를 최종 답변까지 전파하는 신뢰도 표기 체계**
- **문서 반영 필요**: `chat-agent-plan.md` 배경/핵심설계결정3/로드맵E단계에 이 확장 시나리오를 명시적으로 기록

### 후속 조치 (2차)

1. `chat-agent-plan.md`에 "관련기업 발견 후 기존 3개 tool 반복 적용 + 교차 영향 종합" 문장 추가
2. 향후 구현 시 `MAX_TICKERS_PER_QUERY`, `MAX_LLM_CALLS_PER_QUERY` 같은 질의 단위 예산 상한을 설계에 포함(기존 배치용 `max_calls_per_run`과는 별개 개념임을 명확히 구분)
3. 관계 확인/추정 플래그 전파 및 confidence 하향 규칙을 "관련기업 탐색" 착수 시(로드맵 E단계) 설계에 포함
4. 이번에도 지금 당장 구현하지 않음(YAGNI 유지) — 로드맵 E단계 착수 시점에 반영

## 7. 3차 논의 (같은 날) — "종목별 딥다이브"에 deepagents(agent-as-tool) 재도입 결정

### 배경

6절(2차 회의)은 "관련기업 각각에 대한 실제 분석(ML/LLM차트/뉴스공시)은 자율 판단이 필요 없는 고정 절차이므로 sub-agent가 불필요하다"고 결론 냈다. 이후 사용자가 향후 확장성을 우선순위로 두겠다는 방향을 명확히 하면서, 종목별 분석의 스코프를 "고정 3단계"가 아니라 **"필요하면 스스로 판단해 추가 조사"**까지 포함하도록 확정했다. 이 스코프 변경이 6절 결론이 의존했던 전제("자율 판단 불필요")를 실제로 무효화한다.

### 결론

**6절의 "종목별 sub-agent 불필요" 결론을 이 새 스코프에 한해 뒤집는다.** 자율 다단계 판단 + 검증이 실제로 필요해졌으므로, 이 프로젝트가 계속 지켜온 agent 정당화 기준(`chat-agent-plan.md` 핵심 설계 결정 1 — "위임받은 작업이 스스로 몇 스텝을 쓸지 자율적으로 판단해야 하는 경우")을 그대로 적용하면 이번엔 기준을 충족한다. 이건 입장 변경이 아니라, 같은 기준을 새 스코프에 다시 적용한 결과다.

**구현 방식**: LangGraph/deepagents를 "agent-as-tool" 패턴으로 도입한다 — 메인 대화 에이전트 자신은 여전히 단순 네이티브 tool-calling 루프로 유지하고(기존 결정 무변경), 아래 두 지점만 deepagents 서브에이전트로 구현해 메인 에이전트에게는 tool 하나로 노출한다:

1. **`find_related_companies`** — 관계 탐색(후보생성 LLM 1회 → DART/뉴스 검증 → 필요시 재탐색)
2. **`stock_analyst(ticker)`** — 종목별 딥다이브(ML/LLM차트/뉴스공시 3개 tool 호출 → 결과를 보고 스스로 추가 조사 여부 판단)

두 서브에이전트 모두 부모(메인 에이전트) 입장에서는 tool 호출 1번이고, 내부 판단 과정은 격리된 컨텍스트에서 처리돼 부모 컨텍스트를 오염시키지 않는다. 이는 PRD §4가 원래 제안한 "역할별 deepagents 서브에이전트" 구조가 이 프로젝트에서 처음으로 실제 정당화되는 지점이다 — MVP-0/ML #2/LLM차트 #3/메인챗봇 자체는 계속 프레임워크 없이 간다.

```
[메인 대화 에이전트]  ← 여전히 네이티브 tool-calling만 쓰는 단순 supervisor (LangGraph 아님, 기존 결정 유지)
        │
        ├──▶ find_related_companies  [deepagents 서브에이전트 — agent-as-tool]
        │        내부: 후보생성(LLM) → DART/뉴스 검증 → 필요시 재탐색, 스스로 판단
        │        결과: 관련기업 리스트 + 확인/추정 플래그 (부모에겐 이 결과만 보임)
        │
        └──▶ stock_analyst(ticker)  [deepagents 서브에이전트 — agent-as-tool, 종목당 1회]
                 내부: ML/LLM차트/뉴스공시 3개 tool 호출 → 결과 보고 "더 파야 하나" 스스로 판단
                        → 필요하면 DART 재조회·뉴스 재검색 등 추가 조사
                 결과: 이 종목에 대한 종합 판단 + 근거 (부모에겐 이것만 보임)
```

### 반드시 포함해야 할 안전장치

- **재귀/반복 상한**: LangGraph의 `recursion_limit`(또는 상응 설정)을 두 서브에이전트 모두에 필수 적용 — "스스로 판단해 추가 조사"가 무한정 반복되는 것을 방지
- **질의 단위 호출 예산**: `MAX_TICKERS_PER_QUERY`(권장 3~5개), `MAX_LLM_CALLS_PER_QUERY`(권장 6~8회) — 기존 `llm_chart_analyst`의 `max_calls_per_run`(배치 프로세스 단위 상한)과는 별개 개념, 6절의 권고를 그대로 유지
- **신뢰도 전파**: 관계의 "확인됨/추정됨" 플래그, 그리고 이번에 새로 추가되는 "서브에이전트 자율 조사 결과"라는 출처 표기를 최종 답변까지 전파 — 자율 조사가 늘어난 만큼 환각 위험도 커지므로 사용자가 구분할 수 있어야 함

### 새로 발생하는 비용 (정직하게 기록)

- **신규 의존성**: `langchain`/`deepagents`가 `pyproject.toml`에 아직 없음 — 이 프로젝트에서 처음 실제로 도입되는 지점
- **테스트 전략 변경**: 프로젝트 전체가 따르는 "결정론적 모킹 테스트" 원칙이 이 두 서브에이전트의 자율 판단 자체에는 그대로 적용되지 않음 — 합리적 범위를 판정하는 eval 방식 테스트를 병행해야 함
- **환각 위험 재상승**: 자율 조사가 잘못된 방향으로 파고들 위험이 고정 절차보다 커짐 — 위 신뢰도 전파로 완화하되 완전히 제거되지는 않음

### 결론 요약

| 항목 | 상태 |
|---|---|
| `find_related_companies` 구현 방식 | deepagents 서브에이전트 (agent-as-tool) |
| `stock_analyst(ticker)` 구현 방식 | deepagents 서브에이전트 (agent-as-tool), 자율 추가조사 포함 |
| 메인 대화 에이전트 자체 | 변경 없음 — 네이티브 tool-calling 루프 유지 |
| 구현 착수 시점 | 변경 없음 — 로드맵 E단계, 실사용 근거 확인 후 |
