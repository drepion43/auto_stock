# 로드맵 메모 — 멀티에셋 확장·자동매매·백그라운드 에이전트 (오케스트레이터 재검토 트리거)

> 이 문서는 결정 문서가 아니라 **미래 결정을 위한 트리거 기록**이다. 아래 항목이 실제
> 구현 단계에 들어갈 때, 그 시점에 다시 검토해서 정식 설계문서(`*-plan.md`)로 승격한다.
> 지금 당장 아무것도 구현하지 않는다.

## 배경

챗봇 Stage E(`chat-agent-plan.md`/`chat-agent-architecture-review.md`) 구현 중, 사용자가
장기 로드맵을 공유했다: 주식 챗봇을 먼저 완성한 뒤 (1) 비트코인 등 자산군 비교/추천,
(2) 실계좌 연결 + 자동매매(비중 배분 포함), (3) 백그라운드 상시 모니터링 에이전트를
순차적으로 추가할 계획이다. 이 세 가지가 "메인 대화 루프에 LangGraph/deepagents를
지금 도입해야 하는가"라는 질문을 다시 불러왔다. 아래는 그 논의의 결론이다.

> **결정 갱신 (2026-10-05)**: `docs/PRD.md` §9 결정 갱신에 따라 (2) 자동매매(MVP-1 및
> 그 이후) 전체가 현재 우선순위에서 배제됐다 — "주식 챗봇을 먼저 완성한 뒤"라는 이
> 문서의 원래 전제가 그대로 유효해졌을 뿐, 지금은 그 "먼저" 단계(추천 챗봇)에만
> 전적으로 집중한다. 아래 ③(자동매매 실행 워크플로) 논의는 그 트리거 조건이 실제로
> 발생할 때까지 보류되며, ①(멀티에셋 비교)·④(백그라운드 에이전트)도 동일하게 보류다.

## 결론 요약

| 항목 | 지금 필요? | 오케스트레이터 필요? |
|---|---|---|
| ① "주식 vs 비트코인 어디가 좋을까" 비교 질의 | 자산군 추가 시 자연스럽게 지원됨 | **불필요** — native tool-calling의 parallel function call만으로 충분 |
| ② 멀티에셋 비중 배분 **계산** | 자동매매 확장 시 | **불필요** — `risk_sizing.suggest_position`과 동일하게 결정론적 함수로 확장 |
| ③ 자동매매 **실행 워크플로**(제안→승인→체결→기록) | 자동매매 확장 시 | **정당화될 가능성 높음** — 승인 체크포인트가 프로세스 재시작을 견뎌야 한다면 |
| ④ 백그라운드 상시 모니터링 에이전트 | 백그라운드 기능 확장 시 | **정당화될 가능성 높음** — 세션 독립적 지속 실행 + 재시작 내구성 필요 |

**메인 대화 챗봇 루프(`chat_agent/loop.py`)는 위 어느 것에도 해당하지 않는다** — 계속
수동 tool-calling 루프로 간다(`chat-agent-architecture-review.md`의 기존 결정 유지).

## 항목별 근거

### ① 자산군 비교 질의

`OpenAIChatAgentClient.create_response`(`chat_agent/client.py`)는 이미 응답 하나에서
복수의 `function_call`을 리스트로 반환할 수 있다(parallel tool calls). 즉 모델이 한
턴에 `stock_analyst(삼성전자)`와 (미래의) `crypto_analyst(비트코인)`을 동시에 부르고,
두 결과를 받아 텍스트로 비교 종합하는 것이 지금 `loop.py` 구조 그대로 가능하다.
비교는 오케스트레이션 문제가 아니라 "도구 두 개 부르고 결과를 종합 서술"하는 LLM의
기본 tool-calling 동작이다. **비트코인을 추가할 때 필요한 건 새 자산군용 tool/서브에이전트
뿐이고, 메인 루프 코드는 변경 불필요.**

### ② 비중 배분 계산

이 프로젝트는 이미 "정해진 입력 → 구조화된 출력"인 계산(ML예측·공시분석·`risk_sizing.
suggest_position`의 ATR 기반 사이징)에 대해 일관되게 "자율판단 불필요, 결정론적 함수로
구현"이라고 판단해왔다(`chat-agent-architecture-review.md` §6 참고). 멀티에셋 배분도
"보유자산 현황 + 리스크정책(PRD §6 확장판) + 자산군별 신호"를 입력받아 배분안을
산출하는 결정론적 알고리즘으로 확장하면 된다 — LLM이나 그래프가 필요한 지점이 아니다.

### ③ 자동매매 실행 워크플로

배분 **계산**과 실계좌 **실행**은 다른 문제다. 실행은 "주문 제안 → 사용자 승인 대기 →
브로커 API 실행 → 체결 확인 → 상태 기록"이라는 다단계 워크플로이고, 특히 **"승인 대기
중 세션/프로세스가 끊겨도 나중에 재개 가능해야 한다"**는 요구가 실제로 생기면 이는
LangGraph checkpointer류 durable-execution 프레임워크가 정당화되는 지점이다. 이 시점이
오면 `broker-safety-reviewer` 서브에이전트 리뷰와 함께 별도 설계문서로 정식화한다.

### ④ 백그라운드 모니터링 에이전트

사용자가 매 턴 질문해야 응답하는 지금의 반응형 구조와 달리, 조건 충족 시 스스로 행동하는
상시 에이전트는 세션과 무관한 지속 상태 + 재시작 내구성이 필요하다. 이것도 LangGraph 등
durable-execution 프레임워크가 실제 이득을 줄 수 있는 지점이다.

## 왜 메인 챗봇 루프와 분리해서 생각하는가

③④가 실제로 정당화되더라도, **그것이 대화형 리서치 챗봇(`loop.py`)까지 같은 오케스트레이터로
바꿔야 한다는 뜻은 아니다.** 챗봇 루프는 사용자가 타이핑하는 순간에만 짧게 도는 동기적
반응형 루프이고, 백그라운드 에이전트·실행 워크플로는 세션과 무관하게 오래 도는 비동기
프로세스다. 생명주기가 근본적으로 다른 것을 하나의 그래프 런타임에 억지로 통합하면
결합도만 올라가고 실이익이 없다. **필요한 서브시스템에만 붙이고, 챗봇 루프는 계속
가볍게 유지한다.**

## 지금 해두면 좋은 저비용 조치 (선택)

프레임워크 도입 없이도 나중 확장을 덜 아프게 하는 설계 습관:

- `ChatToolContext`/`AccountState`(`chat_agent/tools.py`, `risk_sizing/models.py`) 필드를
  주식 전용으로 하드코딩하지 말고, 자산군(`asset_class` 등) 축을 나중에 얹을 수 있는
  형태로 열어둔다. 지금 당장 필드를 추가하라는 뜻이 아니라, 이름/구조를 주식 전용
  용어로 고정하지 않는 정도의 습관이다.

## 재검토 트리거 (이 문서를 다시 열어야 할 시점)

- 실계좌 연결/자동매매 구현이 실제로 시작될 때 → ②③을 정식 설계문서로 승격
- 백그라운드 실행이 실제로 요구사항에 들어올 때 → ④를 정식 설계문서로 승격
- 비트코인 등 신규 자산군 데이터소스/도구 추가가 시작될 때 → ①이 실제로 잘 동작하는지
  수동 검증 체크리스트에 추가(현재는 이론적 근거만 확인, 실동작 미검증)
