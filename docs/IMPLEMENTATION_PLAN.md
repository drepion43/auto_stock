# auto_stock 구현 계획 (Implementation Plan)

> `docs/PRD.md` §4(시스템 아키텍처)를 실행 가능한 빌드 순서로 구체화한 문서. PRD가 "무엇을·왜"를 정의한다면, 이 문서는 "어떤 순서로·어떻게" 만들지를 정의한다. PRD의 수치·정책이 바뀌면 이 문서도 함께 갱신해야 한다.

## 빌드 순서 요약

**PRD §9에 따라 1차/2차 목표로 나눠 진행한다.** 1차 목표는 자동 주문 실행 없이 "종목 추천까지만" 완성하는 것 — 브로커 API 연동·크리덴셜 관리를 배제해 리스크를 낮추고 추천 엔진의 핵심 가치를 먼저 검증한다.

**1차 목표 (MVP-0, 지금 구현)**:
1. 데이터 수집 계층 (#0)
2. 규칙엔진 (#1)
3. 리스크·포지션 사이징 에이전트 (#5) — **참고용 사이징 제안까지만** (아래 참고)
4. 추천 설명 생성기 (#6)
5. 알림봇 (#7) — **알림 전용**, 주문 트리거 없음 (아래 참고)
6. 오케스트레이터 — **1차: #0~#7을 연결해 "추천까지" end-to-end 완성**

**2차 목표 (MVP-1, 1차 완성 후 착수)**:
7. 주문 실행 에이전트 (#8) — 브로커 모의투자 연동
8. 리스크 에이전트에 손실한도 자동중단 등 "집행" 로직 추가
9. 오케스트레이터에 주문 실행 연결 — **2차: #8까지 연결해 주문 실행 완성**

**신호 소스 확장 (1차 완성 후, 순서 무관하게 병행 가능)**: ML 예측 모듈(#2) → 차트분석 LLM 에이전트(#3) → 뉴스/공시 분석 에이전트(#4)

각 서브에이전트는 `/scaffold-deepagent <이름>` skill로 한 번에 하나씩 스캐폴딩한다 (`.claude/skills/scaffold-deepagent/SKILL.md` 참고).

## 0. 데이터 수집 계층

에이전트가 아닌 공용 인프라 모듈. 대부분의 서브에이전트가 이에 의존하므로 최우선 구축한다.

- **목적**: 시세/차트 데이터(OHLCV)를 확보해 나머지 서브에이전트에 공급 (PRD §7.2)
- **라이브러리 조합**: FinanceDataReader(FDR)로 국내(KRX)+나스닥 개별종목 OHLCV를 통일 조회하고, pykrx는 국내 시가총액·전체 종목리스트 등 FDR이 약한 부분을 보조로 병행한다. 역할 분담은 모듈 docstring에 명시한다.
- **저장/캐싱**: 로컬 SQLite/DuckDB에 OHLCV를 캐싱한다. 전체 상장종목 스캔 + 5년치 백테스트 재사용을 고려해 파일 캐시(Parquet/CSV)보다 쿼리 유연성이 좋은 쪽을 택했다.
- **실시간(장중 반복) 수집**: Kafka 등 메시지 브로커는 1인 사용자·단일 파이프라인 규모에 과도한 인프라라 채택하지 않는다(YAGNI). 대신 APScheduler 또는 asyncio 폴링 루프 + 동시성 제한(세마포어)으로 PRD §7.3("장중 실시간에 가깝게 스캔")을 충족한다. 배치 크기·폴링 주기의 구체 수치는 스캐폴딩 시점에 각 브로커/데이터 API의 rate limit을 확인하며 정한다.
- **인터페이스**: 종목코드+기간 → OHLCV DataFrame. 캐시를 우선 조회하고, 미스 시에만 API를 호출해 캐시에 채운다.
- **테스트**: 캐시 히트/미스 동작, API 실패 시 재시도, 국내/나스닥 혼합 조회, 폴링 루프의 동시성 제한 동작
- **향후 확장**: 2단계(AWS 상시운영, PRD §8) 전환 시 폴링 방식으로 병목이 확인되면 그때 Redis Streams/RQ 등 더 가벼운 큐로 단계적으로 올린다. 처음부터 Kafka급 인프라로 가지 않는다.

## 1. 규칙엔진

- **목적**: 이동평균/RSI/MACD 등 기술적 지표로 1차 매수/매도 후보 필터링 (PRD §4)
- **입력**: #0의 OHLCV
- **출력**: 매수/매도 후보 종목 리스트 + 지표별 근거
- **의존**: #0
- **선정 이유(빌드 순서 1순위)**: 외부 API/LLM 의존이 없어 가장 빠르게 TDD로 검증 가능하고, 이것 하나만으로 파이프라인을 추천→승인→주문까지 끝까지 연결해볼 수 있는 최소 신호 소스다.
- **테스트**: 각 지표 계산 정확성(고정 데이터셋 기준값 대조), 필터링 임계값 동작

## 5. 리스크·포지션 사이징 에이전트

> **1차 목표에서는 참고용 사이징 제안까지만 구현한다.** 일일/월간 손실한도 도달 시 자동매매 중단 같은 "집행(enforcement)" 로직은 주문이 실제로 나가야 의미가 있으므로, 주문 실행 에이전트(#8)와 함께 2차 목표에서 구현한다.

- **목적**: PRD §6에서 확정한 리스크 정책을 코드로 구현 — 종목당 5% 이내, 최대 동시 10종목(총 익스포저 50%), 손절매/익절매 및 포지션 사이징은 ATR(변동성) 기반 동적 조정. **1차 목표 범위**: 위 한도 내에서 "이 종목은 이 정도 수량이 적절합니다"라는 참고용 제안을 계산해 추천에 포함. **2차 목표 범위**: 일일 손실 2%/월간 손실 10% 도달 시 자동매매 중단 등 실제 집행 로직
- **입력**: #1(이후 #2~#4)의 후보+시그널, 현재 계좌 상태
- **출력**: 종목별 참고용 매매 수량 제안, 한도 대비 검증 결과(통과/초과 표시) — 1차 목표에서는 표시만, 차단 실행은 안 함
- **의존**: #1
- **리뷰**: 완료 후 `risk-policy-guardian` 서브에이전트 리뷰 필수
- **테스트**: 각 한도(종목당 5%, 동시 10종목) 대비 계산 정확성, ATR 기반 사이징 계산 정확성. 일일/월간 손실한도 차단 테스트는 2차 목표에서 추가

## 6. 추천 설명 생성기

- **목적**: 신호 계층의 근거를 사람이 이해할 수 있는 2~3문장 자연어로 종합 (PRD §5.1, Explainability)
- **입력**: #1(~#4) + #5의 출력
- **출력**: 근거 설명 텍스트 (예: "RSI 과매도 + 실적 서프라이즈 기사 + LLM 반등 패턴 감지, 신뢰도 XX%")
- **의존**: #1, #5
- **설계 원칙**: MVP 시점에는 규칙엔진 근거만으로 시작하되, 이후 ML/LLM차트/뉴스 신호가 추가되면 자동으로 더 풍부한 설명을 생성하도록 확장 가능한 구조로 설계한다.

## 7. 알림봇

> 1차 목표에서는 **알림 전용**이다 — 승인 UI 요소는 화면/메시지에 남겨둘 수 있지만, 승인해도 실제로 트리거되는 주문이 없다(주문 실행 에이전트가 아직 없음). 2차 목표에서 #8과 연결하며 "승인 → 실제 주문 실행" 흐름이 활성화된다.

- **목적**: 텔레그램 또는 디스코드로 추천 내역 + 근거 설명을 전송 (PRD §4, §3 흐름)
- **입력**: #6의 출력
- **출력 (1차)**: 추천 알림 메시지 전송. **출력 (2차)**: 사용자 승인/거부 신호 → #8로 전달
- **의존**: #6
- **범위**: 첫 구현은 텔레그램/디스코드 중 하나만 (봇 토큰 등 크리덴셜은 반드시 환경변수로 관리)
- **테스트**: 메시지 포맷. 승인/거부 콜백 처리 테스트는 2차 목표(#8 연결 시점)에서 추가

## 2차 목표 (MVP-1): 반자동 주문 실행 추가

아래는 1차 목표(종목 추천까지) 완성 후 착수한다. PRD §9 MVP-1에 해당.

## 8. 주문 실행 에이전트 (2차 목표)

- **목적**: 승인된 주문만 브로커 API로 실행 (PRD §4, §7.1) — 반자동 원칙: 승인 없이는 절대 주문하지 않음
- **입력**: #7의 승인 결과, #5의 수량/한도
- **출력**: 체결 결과
- **의존**: #5(집행 로직 포함하도록 확장), #7(승인 흐름 활성화), 브로커 모의투자 계정(한투 또는 키움)
- **리뷰**: 완료 후 `broker-safety-reviewer` 서브에이전트 리뷰 필수 — 토스증권 Open API는 모의투자를 지원하지 않으므로 검증 단계에서 절대 사용하지 않는다는 점을 재확인
- **테스트**: 미승인 주문 차단, 모의투자 엔드포인트 사용 검증, 크리덴셜 하드코딩 여부 검사

## 오케스트레이터

- **1차 목표**: #0~#7을 PRD §3 흐름의 앞부분(데이터 수집 → 추천 생성 → 참고용 리스크 계산 → 설명 생성 → 알림 전송)대로 연결해 "추천까지" end-to-end 완성 (최초 가동은 규칙엔진 신호만으로)
- **2차 목표**: #8을 연결해 승인 → 주문 실행 → 체결 알림까지 PRD §3 전체 흐름 완성
- **테스트 (1차)**: 데이터 수집 → 추천 생성 → 참고용 리스크 계산 → 설명 생성 → 알림 전송 통합 테스트
- **테스트 (2차)**: 승인 → 주문 실행 → 체결 알림까지 포함한 §3 전체 흐름 통합 테스트

## 신호 소스 확장 (MVP 이후)

MVP가 end-to-end로 동작한 뒤, 아래 순서로 신호 소스를 추가해 추천 품질을 고도화한다. 추천 설명 생성기(#6)는 새 신호가 추가될 때마다 자동으로 더 풍부한 근거를 종합하도록 이미 설계되어 있으므로, 이 확장은 추천 설명 생성기의 재설계 없이 이뤄질 수 있어야 한다.

1. **ML 예측 모듈 (#2)**: 구현 완료 — scikit-learn `LogisticRegression`(L2)로 확정, `explainer.generate_explanation`의 `extra_reasons` 확장 포인트를 경유한 보조 신호로 배선 완료(자체 후보 생성/필터링은 하지 않음). 상세 설계·lookahead 방어·스코프 경계는 `docs/design/ml-predictor.md` 참고. **실제 KRX 전체 유니버스 재학습은 아직 안 됨** — `KRX_ID`/`KRX_PW` 환경변수 설정 후 `scripts/train_ml_model.py` 실행 필요.
2. **차트분석/예측 에이전트 — LLM (#3)**: 차트 데이터를 LLM에 입력해 패턴 해석
3. **뉴스/공시 분석 에이전트 (#4)**: DART(1순위 확정) + 빅카인즈(유력 후보)로 감성·이벤트 추출 (PRD §7.2)

각 확장 단계의 세부 설계(ML 알고리즘 선정, 뉴스-종목 매칭 파이프라인 등)는 착수 시점에 확정한다 — PRD §11 Open Questions에 관련 TBD 항목이 이미 기록되어 있다.
